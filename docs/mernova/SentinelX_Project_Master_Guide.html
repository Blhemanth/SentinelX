1. Executive Summary & Mission Overview

SentinelX is an edge-to-cloud automated threat detection, incident triage, and emergency dispatch synchronization platform. Designed for modern high-density public infrastructure—including transit terminals, commercial facilities, campuses, and municipal venues—SentinelX combines high-performance edge machine learning with enterprise emergency coordination workflows.

💡 In Plain English (Beginner Friendly)

Traditional security guards are overwhelmed by watching dozens of video monitors simultaneously, often missing dangerous events like fights or accidents until it is too late. SentinelX acts like an intelligent co-pilot for security operators. It directly reads the camera feed, uses artificial intelligence to instantly spot emergencies, highlights them on a dashboard, and automatically coordinates with emergency dispatchers—all while ensuring security operators make the final decisions.

⚙️ Technical Engineering Architecture

SentinelX implements a decentralized hybrid surveillance topology. Native client nodes (Flutter Desktop x64) execute low-latency local inference via Microsoft ONNX Runtime C-FFI within an isolated background Dart isolate. Temporal video tensors [1, 16, 3, 224, 224] are evaluated against an embedded neural network (SentinelXNet), streaming authorized threat telemetry to a hardened Node.js Express backend and MongoDB cluster. The Emergency Operations Center (EOC) web client (React 19 + Vite) synchronizes incident progression in real time.

2. Problem Statement, Industry Blind Spots & Motivation

Surveillance infrastructure globally suffers from structural failure modes that compromise physical security:

  • Surveillance Fatigue & Human Error: Psychological studies demonstrate that human video monitors miss over 90% of critical anomaly events after just 20 minutes of continuous monitoring due to cognitive saturation.
  • Excessive Detection-to-Dispatch Latency: In conventional monitoring setups, an anomaly takes between 4 to 12 minutes to be visually noticed, manually verified, and telephonically reported to emergency responders.
  • Cloud Bandwidth Costs & Privacy Vulnerability: Continuous streaming of uncompressed 4K/1080p RTSP camera streams to centralized cloud servers requires massive network bandwidth (exceeding 15 Mbps per camera) and introduces severe regulatory and privacy risks under GDPR and CCPA.
  • Siloed Emergency Operations: Disconnected point solutions force security desks to transcribe coordinates and alerts manually into Computer Aided Dispatch (CAD) systems, increasing human latency.
The SentinelX Objective: Eliminate video surveillance latency and operator cognitive overload by evaluating temporal video tensors directly at the edge, transmitting structured incident metadata only when threats exceed strict thresholds, and providing sub-second cross-client operational synchronization.

3. Proposed Solution & Architectural Innovations

SentinelX addresses these challenges through five foundational architectural innovations:

  1. Decentralized Hybrid Edge-Cloud Inference: Raw video frames never leave the physical facility. Edge devices run local ONNX Runtime inference models natively on host CPU/GPU, transmitting lightweight JSON telemetry packets only upon verified threat detection.
  2. Asynchronous Dart Isolate Threading: Deep learning forward passes take ~1.6s on host CPU. By delegating all native C-FFI tensor processing to a dedicated background Dart isolate (OnnxInferenceWorker), the main Flutter UI isolate runs completely unblocked, achieving 97.53% fluid frame presentation with zero UI freezing.
  3. Bounded Temporal Rolling Buffer: Rather than processing individual isolated static frames (which cannot distinguish walking from running, or falling from sitting), SentinelX buffers a rolling sequence of exactly 16 frames in memory ($2.30 ext{ MB}$ flat footprint), allowing the model to analyze spatio-temporal dynamics.
  4. Cryptographic Protocol v2 HMAC Trust Boundaries: Public client requests are untrusted. Distributed Flutter applications possess zero backend secrets. Microservices authenticate using request-bound Protocol v2 HMAC-SHA256 tokens binding HTTP method, normalized path, SHA-256 body digest, nonce, and timestamp.
  5. Safety-First Automated Triage & Drill Isolation: Security operator oversight is architecturally enforced. The system enforces strict severity precedence rules, strips untrusted client metadata, and cryptographically isolates drill simulations from ever triggering emergency law enforcement dispatch.

5. Edge ONNX Runtime Engine & Background Isolate Architecture

💡 In Plain English (Beginner Friendly)

Running AI directly inside a computer program is heavy work. If you run the AI on the same thread that draws the user interface, the buttons freeze, animations stutter, and the screen locks up for almost 2 seconds every time the AI thinks. SentinelX solves this by creating a dedicated "worker isolate"—a separate invisible process inside the program. The camera hands video frames to this worker, the worker processes the AI in the background, and the user interface stays completely smooth at 60 Hz.

⚙️ Technical Engineering Architecture

In Dart's single-threaded event loop, calling OrtSession.run() synchronously blocks the root UI isolate for ~1,680 ms per forward pass. SentinelX implements OnnxInferenceWorker using Isolate.spawn(). The worker isolate loads native C dynamic libraries (onnxruntime.dll v1.32.0) via C-FFI. Input tensors [1, 16, 3, 224, 224] are transferred across an inter-isolate SendPort in 5.0 ms. The UI thread registers zero blocking, maintaining a 97.53% fluid compositor presentation rate.

6. Temporal Video Ingestion Pipeline & Tensor Mechanics

Single-frame image recognition cannot capture motion signatures essential for anomaly classification (e.g., distinguishing between an aggressive brawl and a handshake, or an explosion flash versus stage lighting). SentinelX implements spatio-temporal video buffering:

  • Physical Camera Ingestion: Evaluated using the physical HP TrueVision HD Camera via the camera_windows plugin, streaming DirectShow/MediaFoundation frames at ~7.33 FPS.
  • High-Performance Skia Resizing: Raw JPEG bytes are decoded and scaled directly to $224 imes 224$ RGB pixels via Flutter's C++ Skia codec in $4.6 ext{ ms}$, bypassing costly Dart heap object allocations.
  • 16-Frame FIFO Ring Buffer: Managed by [TemporalFrameBuffer](file:///b:/SentinelX/lib/core/camera/temporal_frame_buffer.dart). The buffer capacity is strictly fixed at 16 frames ($2.30 ext{ MB}$ memory ceiling). Earliest frames are padded during the initial 16-frame warm-up period.
  • Planar Float32 Normalization: Converts $16 imes 224 imes 224 imes 3$ uint8 bytes into a contiguous planar Float32List of exactly $2{,}408{,}448 ext{ elements}$ ($9.63 ext{ MB}$) normalized according to ImageNet standards: $$R_{ ext{norm}} = rac{r - 0.485}{0.229}, \quad G_{ ext{norm}} = rac{g - 0.456}{0.224}, \quad B_{ ext{norm}} = rac{b - 0.406}{0.225}$$
  • Acoustic Silence Baseline: To fulfill the multimodal input contract of SentinelXNet in Phase 4.3.5.1, the audio input tensor is populated with a synthetic calibrated silence baseline of [1, 1, 128, 128] at $-80.0 ext{ dB}$, safely enforcing degraded video-only operation.

7. Dual-Token Authentication, Session Whitelisting & RBAC

💡 In Plain English (Beginner Friendly)

Just like a bank vault requires two separate keys, SentinelX protects user access with two tokens. When an operator logs in, they receive a short-lived "access pass" (lasts only 15 minutes) and a secure "vault key" (lasts 7 days). If an attacker steals the access pass, it becomes useless in minutes. If an operator logs out or is fired, the server immediately revokes their session in the database, blocking all future access instantly.

⚙️ Technical Engineering Architecture

Authentication implements an enterprise dual-token JWT lifecycle. Short-lived Access Tokens ($15 ext{ minutes}$, signed with HS256) are transmitted via the Authorization: Bearer header. Long-lived Refresh Tokens ($7 ext{ days}$) are persisted in MongoDB with active session IDs. Refresh operations enforce strict token rotation: using a refresh token revokes it and issues a fresh pair. Logout immediately deletes the session record, providing instant server-side revocation.

8. Internal Service Cryptography & HMAC Trust Boundaries

One of the most critical security findings resolved in Phase 4.3.5.1 is the absolute isolation of client applications from internal cryptographic secrets:

  • No HMAC Secrets in Distributed Clients: An internal HMAC secret (INTERNAL_SERVICE_KEY) must NEVER be packaged inside Flutter Windows or Android binaries. Any client decompilation or memory dump would leak the secret.
  • Public Requests are Untrusted: All client requests submitted via POST /api/logs pass through strict server-side sanitization:
    1. req.body.severity is deleted and computed server-side via CrimeLog.calculateSeverity().
    2. req.body.isEmergencyEligible is stripped and forced to false for all client submissions.
    3. Client-declared detectionSource: 'ml_real' is demoted to manual_entry and low_confidence_review.
  • Protocol v2 HMAC Request Binding: When trusted internal backend services (such as the Python ML microservice or server audio verifier) communicate with Express, requests are authenticated with Protocol v2 HMAC tokens: $$ ext{Payload} = exttt{METHOD} : exttt{PATH} : exttt{serviceId} : exttt{timestamp} : exttt{nonce} : ext{SHA256}( exttt{Body})$$ $$ ext{Token} = exttt{v2} . \langle ext{serviceId} angle . \langle ext{timestamp} angle . \langle ext{nonce} angle . ext{HMAC-SHA256}_{ ext{key}}( ext{Payload})$$
  • Timing-Safe Comparison & Replay Cache: Signatures are evaluated using constant-time comparison (crypto.timingSafeEqual). Nonces are tracked in a sliding memory cache with a 60-second freshness window. Protocol v1 tokens are strictly rejected in production.

12. Current Limitations, Technical Debt & Roadmap to Phase 4.4

  • Limitation 1: Video-Only Degraded Baseline: The active model asset requires multimodal input: video tensor `[1, 16, 3, 224, 224]` and audio spectrogram `[1, 1, 128, 128]`. Because hardware microphone ingestion is scheduled for Phase 4.4, the audio input currently receives a synthetic $-80.0 ext{ dB}$ silence spectrogram. The UI displays an amber DEGRADED MODE banner to maintain operator transparency.
  • Limitation 2: CPU Inference Throughput: Host CPU AVX2 execution averages $pprox 1.6 - 2.5 ext{ seconds}$ per inference pass ($0.38 - 0.58 ext{ FPS}$). While completely adequate for anomaly sampling every 2 seconds, it does not provide 30 FPS video evaluation. Upgrading to DirectML GPU acceleration will increase throughput to $>10 ext{ FPS}$.
  • Limitation 3: Single-Instance Nonce Replay Cache: Replay attack protection relies on an in-memory sliding nonce cache. While optimal for single-node deployments, horizontal scaling across clustered Express instances requires an external Redis cache.
